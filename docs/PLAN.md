# threadsdelete build plan

Derived from docs/SPEC.md v0.2 on 2026-10-23. SPEC.md wins over this file.

## Decisions

- Phases → the plan follows SPEC section 8's four phases in order; task IDs use the SPEC phase numbers (P1 Feasibility, P2 Local preview, P3 Removal and useful tests, P4 Automation and handoff).
- SPEC section 9 open questions (fees, eligibility, permissions, categories, host/version, payloads, quotas, token lifetime) → resolved by research tasks P1-01 and P1-02 in `docs/RESEARCH.md`, as SPEC section 8 Phase 1 directs, and gated by P1-03. They are not decided in this plan; later tasks read the answers from `docs/RESEARCH.md` § Contracts.
- Go/no-go → P1-03 writes `Decision: GO` or `Decision: NO-GO` in `docs/RESEARCH.md` § Conclusion. NO-GO marks P1-03 blocked, which auto-skips every later implementation task (all depend on it transitively through P2-01). This is SPEC section 1's "stop and ask".
- Meta documentation that cannot be retrieved → record the failed URL and date, carry SPEC section 9's starting evidence as "documentation finding, not revalidated", never invent a contract. Only positive evidence (a documented fee, no delete endpoint, a required paid tier, a materially different design) yields NO-GO. Rationale: SPEC notes Meta's docs blocked retrieval while drafting; inability to fetch is not evidence of infeasibility.
- Project setup lives in Phase 2 (P2-01), as SPEC section 8 says. The Python verify commands carry `"from": "P2-01"` in `docs/kukulu.json`; during Phase 1 only the `docs/RESEARCH.md` heading check is active.
- HTTP client → `httpx`. It is maintained, typed, and `httpx.MockTransport` is the fake HTTP transport SPEC section 8 Phase 3 asks for, so tests need no extra dependency.
- Token transport → `Authorization: Bearer <token>` header unless `docs/RESEARCH.md` § Contracts → Authentication transport says the API accepts only the `access_token` query parameter. Rationale: keeps the token out of URLs, which httpx and proxies log.
- Empty or whitespace-only environment values are treated as unset and resolve to the documented default. Rationale: GitHub Actions yields `""` for a missing Variable (SPEC section 5); this keeps every default in `threadsdelete/config.py` and lets the workflow pass `${{ vars.KEY }}` with no duplicated literal.
- `DAYS_AGO` upper bound 36500 → values above it are a configuration error. Rationale: prevents `timedelta` overflow; it predates Threads by decades, so it never excludes real content.
- `THREADS_USER_ID` must be a non-empty string of ASCII digits; `THREADS_API_VERSION` must match `^v[0-9]+\.[0-9]+$`. Rationale: Threads IDs and Graph-style versions have these shapes; the check catches pasted tokens or typos before network activity.
- Exit statuses → 0 success/deferral/nothing eligible, 1 runtime failure (incomplete discovery, failed or unknown removal outcome, unrecoverable API error), 2 invalid configuration or usage, 3 authentication, permission or identity-mismatch failure. Rationale: SPEC section 6 requires nonzero; distinct codes make tests and troubleshooting precise.
- An unknown mutation outcome (timeout, connection loss, 5xx or malformed success body on a removal) stops further removals for that run; remaining allowed items count as deferred and the run exits 1. Rationale: SPEC section 3 forbids blind retry; continuing into a likely outage would spend quota on more unknown outcomes.
- Quota inspection unavailable or failing in a removal run → proceed within `MAX_DELETIONS_PER_RUN`, stop at the first documented quota-exhaustion error, defer the rest, and print `Quota: unavailable` with the fallback named in `docs/RESEARCH.md`. Rationale: SPEC section 6 forbids inventing an endpoint or claiming the cap proves quota; the API enforces its own quota.
- Duplicate records → deduplicated by (operation, target ID); the same key with two different action timestamps aborts selection as ambiguous. Rationale: SPEC section 3 dedup plus "abort on ambiguous" safety.
- Pagination → continue while the page has `paging.next`; request the next page through our own base URL with the `paging.cursors.after` cursor; never follow a URL from the response; a repeated cursor, or `next` without an `after` cursor, is a discovery failure. `docs/RESEARCH.md` § Contracts → Pagination wins if it documents a different scheme.
- Discovery never requests the post `text` field. Rationale: SPEC section 3 says avoid logging post bodies; not fetching them is the strongest form.
- Dry run → the `ThreadsClient` is constructed `read_only=True` and refuses any non-GET request before it reaches the transport. Rationale: SPEC section 3 "no mutations, regardless of HTTP method", enforced in one place.
- No token helper, no refresh, no app secret in code (SPEC section 4 makes the helper optional). `docs/META_SETUP.md` gives manual `curl` steps instead. Rationale: smallest design; automatic renewal is a non-goal.
- Bluesky source is not adapted; code is written fresh, so no MIT notice is required. README credits blueskydelete as the reference. If an implementer does adapt code, they must add the notice (CLAUDE.md constraint).
- Report output (account, cutoff, mode, candidates, summary) goes to stdout; diagnostics go to stderr through `logging` with a redacting filter. The summary block starts with the exact line `=== Summary ===` so the workflow can extract it.
- `THREADS_USER_ID` is a GitHub Actions Variable, not a Secret (it is an identifier, not a credential); `THREADS_ACCESS_TOKEN` is the only Secret.
- `workflow_dispatch` has a `dry_run` choice input (`true` default, or `variable` to follow the `DRY_RUN` Variable), so a manual run is a preview unless the owner chooses otherwise.
- ⚠️ ASSUMPTION tuning → P2-06 tunes the three HTTP keys together (they bound one read chain), P3-04 tunes `MAX_DELETIONS_PER_RUN`, P4-03 tunes the workflow's `timeout-minutes`. Measurements are offline (fake transport, fake sleep, arithmetic on the measured attempt and wait counts); live numbers are recorded as pending.
- Parallel streams → none. The plan is small, files are shared between consecutive tasks, and the fresh-worktree setup would add risk without saving meaningful time.
- `uv run --env-file` precedence → verified on uv 0.13.5 (2026-10-23): a variable already set in the process environment wins over the same key in the env file, which is what SPEC section 5 requires. README states it; `scripts/run.sh` relies on it.

## Conventions

- Commit title `<ID>: <title>`; body per CLAUDE.md `## Commit template`.
- Shared module names, types, exit codes and protocols are in CLAUDE.md (`## Module map`, `## Task protocols`); tasks restate what they rely on.
- "RESEARCH" means `docs/RESEARCH.md`, written in Phase 1. Its § Contracts wins over this plan on API facts (endpoints, fields, codes); SPEC wins on behavior.
- Every phase ends with a serial push-and-manual-check task.

### P2-03: Core candidate types, timestamps and eligibility

**Goal:** Implement `threadsdelete/core.py`: categories, operations, candidates, strict timestamp parsing, cutoff, eligibility, deduplicated deterministic selection, result counters and exit codes.
**Files touched:** `threadsdelete/core.py`, `tests/test_core.py`
**Design constraints:** SPEC section 3 (one UTC run-start; eligibility `action_timestamp <= run_started_at - timedelta(days=DAYS_AGO)`; selection takes time as an argument, no network/environment/filesystem/sleep; reject malformed or naive timestamps; dedupe by operation/type and ID; sort by action timestamp, type, then ID), section 5 (candidate fields; result counts). Constraints: `core-is-pure`, `no-wall-clock-in-package` — standard library only (`dataclasses`, `datetime`, `enum`, `collections.abc` and similar), no I/O, no clock, no logging. Define: `Category(StrEnum)` `POST="post"`, `REPLY="reply"`, `QUOTE="quote"`, `REPOST="repost"`, `LIKE="like"`; `Operation(StrEnum)` `DELETE="delete"`, `UNREPOST="unrepost"`, `UNLIKE="unlike"`; `OPERATION_FOR: Mapping[Category, Operation]` (post/reply/quote → DELETE, repost → UNREPOST, like → UNLIKE); frozen dataclass `Candidate(category: Category, target_id: str, action_at: datetime, permalink: str | None)` with property `operation`; `TimestampError(ValueError)`; `parse_timestamp(value: object) -> datetime` accepting only `str` ISO 8601 with a UTC offset (Threads uses `2024-01-31T12:00:00+0000`; also accept `Z` and `+00:00`), rejecting naive, date-only, empty and non-string values, returning an aware UTC datetime; `compute_cutoff(run_started_at: datetime, days_ago: int) -> datetime` raising `ValueError` for naive input; `is_eligible(candidate: Candidate, cutoff: datetime) -> bool` (`<=`); `SelectionError(ValueError)`; `select_eligible(candidates: Iterable[Candidate], cutoff: datetime) -> list[Candidate]` — filters eligible, dedupes by `(operation, target_id)` (same key with different `action_at` → `SelectionError`), sorts by `(action_at, category.value, target_id)`; mutable dataclass `CategoryCounts` with int fields `scanned, eligible, would_remove, removed, failed, unknown_outcome, deferred` (default 0); `QuotaStatus(StrEnum)` `AVAILABLE`, `UNAVAILABLE`, `NOT_CHECKED`; dataclass `RunSummary(counts: dict[Category, CategoryCounts], discovery_complete: bool = True, quota_status: QuotaStatus = NOT_CHECKED, auth_failed: bool = False, notes: list[str])`; `ExitCode(IntEnum)` `OK=0`, `FAILURE=1`, `CONFIG=2`, `AUTH=3`.
**Acceptance tests:** `tests/test_core.py`: `test_cutoff_boundary_before_at_after` (one second before, exactly at, one second after the cutoff), `test_zero_days_includes_content_up_to_run_start` (an item after run start is excluded), `test_offsets_are_normalised_to_utc` (`+0000`, `Z`, `-0800` describing the same instant compare equal), `test_malformed_and_naive_timestamps_rejected` (naive, date-only, garbage, empty, `None`, int), `test_naive_run_start_rejected`, `test_like_and_repost_use_action_time` (a repost candidate whose action time is recent is not eligible even though the label says the original post is old — build candidates with the action time only, asserting the selection uses `action_at`), `test_duplicates_collapse_and_order_is_deterministic` (unordered input with duplicates → sorted, unique; shuffled input gives identical output), `test_conflicting_duplicate_timestamps_raise`.
**Out of scope:** API record parsing (P2-05), budget/quota splitting (P2-07), output formatting.
**Verification:** full verify set; `uv run python -m unittest tests.test_core -v`.
**Depends on:** P2-01

### P2-04: API client transport, pagination, retries and redaction

**Goal:** Implement the read side of `threadsdelete/api.py`: a `ThreadsClient` with trusted-host requests, response validation, sanitized error classification, bounded read retries, cursor pagination, a read-only guard, identity lookup and redaction helpers.
**Files touched:** `threadsdelete/api.py`, `tests/fakes.py`, `tests/fixtures/me.json`, `tests/test_api.py`
**Design constraints:** SPEC section 3 (bounded read retries; redaction), section 6 API adapter (validate bodies and status; stop on auth/permission loss; never reinterpret unknown errors; follow cursors including empty pages; reject repeated cursors; credential-bearing requests only on the trusted host). Follow the research-contract protocol in CLAUDE.md for host, version, auth transport, identity, pagination and error codes. Constraints: `no-wall-clock-in-package`, `no-token-in-logs`, `no-redirects-or-insecure-tls`, `no-post-body-field`, `single-http-client`, `no-token-renewal-or-app-secret`; the four ⚠️ ASSUMPTION values arrive as constructor arguments, never literals (`no-hardcoded-assumption-defaults`). Define: `API_HOST` (from RESEARCH; expected `graph.threads.net`); `Transport = httpx.BaseTransport`; `Identity(user_id: str, username: str)` frozen dataclass; exceptions `ApiError(Exception)` (message already sanitized) with subclasses `AuthError`, `ResponseError` (bad status/body/pagination/untrusted URL), `ReadFailedError` (retry budget exhausted or Retry-After above the maximum), `QuotaExceededError`, `ItemError`, `UnknownOutcomeError`, `MutationBlockedError`, `OwnershipError`. `ThreadsClient(*, access_token: str, api_version: str, timeout_seconds: float, max_read_retries: int, max_retry_wait_seconds: float, read_only: bool, transport: Transport | None = None, sleep: Callable[[float], None] = time.sleep)` wraps one `httpx.Client(base_url=f"https://{API_HOST}/{api_version}/", timeout=timeout_seconds, follow_redirects=False, transport=transport)`; supports `close()` and context-manager use. Token goes in `Authorization: Bearer` (or query parameter only if RESEARCH requires it). Any request whose method is not GET raises `MutationBlockedError` before the transport when `read_only` is True. GET retry policy: retry on `httpx.TimeoutException`, `httpx.TransportError`, HTTP 429/500/502/503/504 up to `max_read_retries` extra attempts; wait = `Retry-After` seconds if present, else `min(2 ** attempt, max_retry_wait_seconds)`; if `Retry-After` exceeds `max_retry_wait_seconds`, stop immediately with `ReadFailedError`; waits go through the injected `sleep`. ## Spec issues

- SPEC section 5 says missing Actions Variables "must resolve to documented defaults rather than invalid empty strings", but section 3 says only `true`/`false` are valid booleans. Resolution: config treats empty and whitespace-only values as unset (default), so an unset Variable passed as `""` is valid; anything non-empty must still be a valid value.
- SPEC section 3 "Exclude known unsupported categories during phase 1" reads as if exclusion happens in Phase 1, which has no code. Resolution: Phase 1 research determines the unsupported set; P2-05 encodes it as `UNSUPPORTED_CATEGORIES` and the preview prints each exclusion.
- SPEC section 8 Phase 1 asks for live observations, but section 1 forbids account setup without separate authorization. Resolution: Phase 1 findings are all `[doc]`; live observations are listed under § Untested and pending and in the phase-end manual checks.
- SPEC section 5 lists `THREADS_USER_ID` without saying Secret or Variable. Resolution: Variable (an identifier, not a credential).
- SPEC section 6 requires exits for "deliberate quota/cap deferral" to be 0 but does not cover a quota error that arrives mid-run. Resolution: treat a documented quota-exhaustion error as quota deferral (exit 0 if nothing failed); an undocumented error is never treated as quota.
- SPEC section 6 does not say whether removals continue after an unknown outcome. Resolution: stop and defer the rest (Decisions).
- SPEC section 7's "Build/syntax check" is not a CI-only concern; it is listed in `docs/kukulu.json` `build` and run in CI and P4-06, not after every task.
